# Postgres and MongoDB back up to Cloudflare R2 in R2's own words, and restore from it, proven live on GKE

## What changed

- **`KubernetesPostgres` and `KubernetesMongodb` gain an `r2` backup arm.** Until now an R2 bucket was reachable only by dressing it as S3: an endpoint host copied from Cloudflare's site, a region of `auto`, a key pair minted in the dashboard. The `r2` arm is declared in R2's vocabulary: the bucket's `account_id` and `jurisdiction` (both references onto a `CloudflareR2Bucket`; on Mongo the `bucket` name is a reference too — the catalog's first bucket reference from a Kubernetes kind) and a `credentials` pair (`access_key_id`, `secret_access_key`, references onto a `CloudflareAccountApiToken`; a dashboard-minted pair fits the same two fields as literals). Both engines compose the S3 dialect underneath: the jurisdiction's endpoint (`https://<account>.r2.cloudflarestorage.com`, or `.eu.`/`.fedramp.`/`.us.` — a jurisdictional bucket answers only on its own host), region `auto`, path-style addressing on Mongo, and on Postgres the Barman plugin sidecar's `AWS_REQUEST_CHECKSUM_CALCULATION`/`AWS_RESPONSE_CHECKSUM_VALIDATION=when_required` posture (boto3's data-integrity checksums, the plugin's documented fix for S3-compatible stores). On Postgres the bucket stays inside `destination_path` (`s3://<bucket>/<path>`), exactly like the `gcs` and `azure_blob` arms; a fourth path-scheme rule enforces it. No keyless posture exists for R2 from any cluster, and the arms say so.
- **`CloudflareAccountApiToken` exports itself as the S3 credential R2 authenticates.** Cloudflare's rule — access key id = the token's id, secret access key = SHA-256 of its value — is a property of the token, so the token kind now exports `r2_access_key_id` and `r2_secret_access_key` (sensitive; `pulumi.ToSecret` and `sensitive = true`). Every S3-compatible arm already in the catalog (Velero, Harbor, MLflow, Loki, Tempo, the `s3` arms) can take R2 credentials by reference from this release on; no database module hashes anything.
- **`CloudflareR2Bucket` tells the truth about where it lives.** New outputs `account_id`, `jurisdiction` (normalized: `default` when empty), `s3_endpoint`; and `bucket_url` — hardcoded to the default host in BOTH engines — is now composed from the jurisdiction's endpoint (it was wrong for every eu/fedramp/us bucket). `pkg/cloudflare/r2` holds R2's host table and the derivation once, with unit tests pinned to Cloudflare's documented examples; the Terraform twins carry the table in HCL under a comment naming the Go source of truth.
- **Two live catches fixed or taught at the root, both store-independent.** (1) A Percona MongoDB Restore declared together with a fresh multi-member cluster is parked in a terminal `get backup meta: not found`: the operator sends its metadata resync before any pbm-agent is listening (agents restart through the replica set's first authentication; PBM commands are pulled from "now", so an early command is simply missed), the 30-second resync-start deadline expires, and the restore controller never retries. Both modules now wait for the cluster to report `ready` before creating the Restore — `pulumi.com/waitFor: jsonpath={.status.state}=ready` (30-minute timeout) and the alekc `wait_for { field { key = "status.state" value = "ready" } }` — ONLY when `spec.restore` is declared; a cluster without a restore keeps the never-block-on-a-controller posture. (2) A cluster carrying cert-manager's CRDs without its webhook (a half-uninstalled cert-manager, or the CRDs another install kept) blocks every Percona MongoDB cluster before its first pod: the operator's dry-run `CertificateRequest` probe fails with "the cert-manager mutation webhook did not mutate". Taught on the Mongo `tls` field, the GUIDE, and the harness README (sweep the CRDs between a Postgres-backup lane and a Percona lane on the shared kind cluster).
- **Corrected claims.** Both Postgres engines' comment that the region Secret "works identically for the keyless posture" — barman-cloud reads it only on the declared-key path. The Mongo `controls.yaml` sentence claiming an empty `gcs.service_account_key_json` uses GKE Workload Identity — PBM has no Workload Identity path (WA-009's class, missed by the earlier fix).
- **E2E.** The `gcp-gke` batch declares its Cloudflare side from the catalog (`manifests/04-r2-backup-store.yaml`: one bucket, one token scoped to it with `Workers R2 Storage Bucket Item Write`); `bootstrap.sh` publishes `PLANTON_E2E_GKE_R2_*`; `teardown.sh` empties the bucket over the S3 API before destroying (R2 refuses a non-empty bucket, the provider has no force-destroy); `audit.sh` checks both. Four new real-cluster scenarios: Postgres `gke-r2-recovery`, Mongo `gke-r2-restore`, and their fixtures. The two seed scripts are store-neutral (`gke-recovery-seed.setup.sh`, `gke-restore-seed.setup.sh`) and serve the GCS and R2 scenarios alike; the verifier dispatch matches any `gke-*-recovery`/`gke-*-restore` scenario.
- **Presets and reader surfaces.** `kubernetespostgres/presets/05-gke-ha-r2-backups`, `kubernetesmongodb/presets/04-gke-replica-set-r2-backups`; GUIDE sections "Disaster recovery on GKE with Cloudflare R2: the resource set" on both kinds (token → bucket → plugin → database → recovery target) and "A half-uninstalled cert-manager blocks every cluster" on Mongo; README/catalog.md/controls/cost/IaC READMEs; `reference.md` and cost estimates regenerated (the Mongo estimate model gains its two GKE presets — 03 had been missing since it shipped).
- **Update rule.** Two teachings beside the keyless-claim probe: an S3-compatible store gets its own arm in ITS vocabulary and the module does the S3 translation (read the store's compatibility matrix, the CRD, and the CLIENT's defaults; the checksum posture belongs in the module); and a one-shot controller verb waits for the state its controller assumes — the exception to never-block-on-a-controller, proven from the controller's log first.
- **Small fixes riding along.** `planton tofu generate-variables --output-file` ends the file with a newline (every regen used to leave a "no newline at end of file" hunk); the finops preset-replay test counts the Postgres preset directory instead of pinning `3` (it had been red since the fourth preset shipped); the two `BUILD.bazel` files 057 forgot for the Barman plugin kind's Pulumi module.

## Why

A team that keeps its backups in Cloudflare R2 should not have to lie to Planton about what R2 is. Declaring the bucket and the token from the catalog and pointing the database at them by reference is the shape every other cross-resource input in the catalog already has; the S3 dialect — endpoint by jurisdiction, region `auto`, addressing style, checksum posture, the token as a key pair — is Cloudflare's business and the module's, never the operator's. Putting the credential derivation in the token kind rather than in each consumer made the whole catalog R2-capable in one move. The two operator behaviors caught live would have bitten adopters on ANY store; GCS in the previous session passed by timing.

## How to check

```bash
go test ./catalog/kubernetes/kubernetespostgres/... ./catalog/kubernetes/kubernetesmongodb/... ./catalog/cloudflare/cloudflarer2bucket/... ./catalog/cloudflare/cloudflareaccountapitoken/... ./pkg/cloudflare/r2/ ./pkg/outputs/ ./pkg/refcheck/ ./pkg/secretcoverage/ ./pkg/presetvalidity/ ./pkg/finops/... ./pkg/compliance/...
# Live on kind (both engines; the MinIO regression gates, unchanged behavior):
go test -tags=e2e -run 'TestKubernetesPostgres_(Pulumi|Terraform)/with-backup' ./e2e/
go test -tags=e2e -run 'TestKubernetesMongodb_(Pulumi|Terraform)/with-backup' ./e2e/
# Live on a GKE cluster that already runs CloudNativePG and cert-manager, with a Cloudflare account:
CLOUDFLARE_API_TOKEN=... CLOUDFLARE_ACCOUNT_ID=... catalog/kubernetes/aa_e2e/realcluster/gcp-gke/bootstrap.sh && source ~/.planton-e2e/planton-e2e-gke/env.sh
go test -tags=e2e -run 'TestKubernetesPostgres_(Pulumi|Terraform)/gke-r2-recovery' ./e2e/
go test -tags=e2e -run 'TestKubernetesMongodb_(Pulumi|Terraform)/gke-r2-restore' ./e2e/
catalog/kubernetes/aa_e2e/realcluster/gcp-gke/teardown.sh && catalog/kubernetes/aa_e2e/realcluster/gcp-gke/audit.sh
```

The Postgres recovery proof reads both markers (base backup restored; WAL archived after it replayed), the source's credential over the recovered `-rw` Service, and one node per instance; the Mongo restore proof reads the Restore's `ready`, both markers (the second via PITR), the source's credential, and the node spread. All four lanes passed on both engines against R2 with a token scoped to the single bucket, and the Terraform lanes with the blind import round-trip.
