# The Barman Cloud backup plugin is its own kind, and the CloudNativePG operator is only the operator

## What changed

- **New kind: `KubernetesCnpgBarmanCloudPlugin`.** Installs the Barman Cloud plugin for CloudNativePG from the official Helm chart (`plugin-barman-cloud` 0.7.0 = plugin v0.13.0) as one fixed-name release, `plugin-barman-cloud`, in the operator's namespace. The spec is the flat Helm-kind surface: `namespace` (a reference whose default kind is `KubernetesCloudNativePgOperator`'s `namespace` output, so a bare `valueFrom` naming the operator resource puts the plugin where the operator can discover it and orders it after the operator; a literal names a CloudNativePG someone else installed), `create_namespace`, `chart_version`, `crds.install`, `replicas`, `resources`, `image` and `sidecar_image` (both in the chart's split registry/repository shape, so a mirror never renders under the default registry), `image_pull_secrets`, `priority_class_name`, `node_selector`, `tolerations`, `helm_values`. The chart's fixed identities (`service.name`, the name overrides) are re-pinned after the escape hatch on both engines. Outputs: `namespace`, `release_name`, `plugin_name`. Registry prerequisites: `KubernetesCertManager` and `KubernetesCloudNativePgOperator`. Presets `01-standard` (beside the catalog operator, by reference) and `02-beside-resident-operator` (a literal operator namespace).
- **`KubernetesCloudNativePgOperator` loses the plugin.** `barman_cloud_plugin` and `install_operator`, their two validation rules, the second Helm release, and the `barman_plugin_release_name` output are gone; fields renumber contiguously. The kind installs exactly one release, `cnpg`. The `02-with-backup-plugin` preset retires; the operator's docs point at the plugin kind and keep the two teachings that still belong here: one installation per cluster, and the leftover-CRD Helm-ownership trap after a non-Helm uninstall.
- **`KubernetesPostgres` names the real prerequisite and the real symptom.** The `backup` block and the object-store `bootstrap.recovery` require `KubernetesCnpgBarmanCloudPlugin` in the operator's namespace; without it the operator parks the Cluster in the phase "Cluster cannot proceed to reconciliation due to an unknown plugin being required" and never creates its instances (read from the operator's source at v1.30.0 -- the earlier "silently inert" wording was wrong: it is loud in `kubectl get cluster` and invisible only to an apply waiting on Ready). The E2E verifier now asserts the plugin's presence FIRST on any backup- or recovery-declaring lane and names the remedy in its failure sentence.
- **E2E: the plugin is a scenario prerequisite of the backup block, not of every database.** The Postgres `with-backup` and `gke-gcs-recovery` scenarios declare `KubernetesCnpgBarmanCloudPlugin` in `e2e-prerequisites`; its own registry edges bring cert-manager and the operator. The GKE recovery lane declares CloudNativePG and cert-manager resident and adds only the plugin -- the earlier substitute install profile (`install_operator: false`) is gone with the field. The operator kind's `with-barman-plugin` and `plugin-only` scenarios retire; the plugin kind's `install` (kind) and `beside-resident-operator` (`gcp-gke`) scenarios replace them, with a verifier that asserts the plugin Deployment, its `cnpg.io/pluginName` Service, the ObjectStore CRD, and -- beside a resident operator -- that the operator survives the plugin's destroy. Tier-1 entrypoints and regexes wired.
- **Charts.** The six charts that install CloudNativePG re-point their operator template comments and day-2 README notes to the plugin kind; rendered output is unchanged (`chart validate --all`: 18/18).
- **Forge rule.** Real-cluster lanes: prefer declaring the resident and adding the missing sibling kind over substituting a posture-flipped profile -- a kind whose install profile needs a boolean to become "only the part the cluster lacks" is two kinds.

## Why

A cluster that already runs CloudNativePG (every self-hosted Planton does: the platform operator installs one for its own database) needs the Barman Cloud plugin before any catalog Postgres can back itself up. The previous answer -- `install_operator: false` plus `barman_cloud_plugin.enabled` on the operator kind -- worked and was the wrong shape: a boolean that flips what a resource IS, policed by two rules whose only job was to keep half the kind's fields from being dead configuration. The operator and the plugin are different charts, different pins (operator chart 0.29.0 = CloudNativePG 1.30.0; plugin chart 0.7.0 = plugin v0.13.0), different dependencies (the plugin needs cert-manager; the operator does not), and -- on that self-hosted cluster -- different owners. The catalog's grain is one block per lifecycle, and CloudNativePG's own rule settles where the block lives: the operator discovers plugin Services only in its own namespace. A platform operator that installs CloudNativePG can now render the same plugin chart at the same pin behind its own toggle, and the catalog's proof lanes stand in for its plugin behavior.

```bash
# Live on kind (both engines; the Terraform lanes with the blind import round-trip):

PLANTON_E2E_CLUSTER_PROFILE=gcp-gke go test -tags=e2e -run 'TestKubernetesCnpgBarmanCloudPlugin_(Pulumi|Terraform)/beside-resident-operator' ./e2e/

```
