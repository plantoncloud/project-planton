# The platform backs up its own database and comes back from it, and the operator owns the backup plugin

## What changed

- **`spec.database.postgresql.backup` on `PlantonPlatform`.** Declares where the platform's own PostgreSQL is backed up: an `objectStore` with exactly one backend -- `s3` (Amazon S3 or any S3-compatible endpoint), `gcs`, `azureBlob`, or `r2` (Cloudflare R2 through its S3 API; the endpoint follows from `accountId` and `jurisdiction`, the only region R2 accepts is set for you) -- a `retentionPolicy` (default `30d`), a `schedule` (six-field cron, seconds first; default daily at 02:00 UTC), and `serviceAccountAnnotations` for keyless cloud identity on the database's own ServiceAccount (CloudNativePG names it after the cluster). Keys, when used, live in an adopter-owned Secret the declaration names (`credentialsSecretName`; `ACCESS_KEY_ID`/`SECRET_ACCESS_KEY`, `APPLICATION_CREDENTIALS`, `AZURE_STORAGE_CONNECTION_STRING`), preflighted before anything renders. The operator renders the plugin's `ObjectStore`, the settings Secret the plugin insists on for non-secret values (region, storage account), the Cluster's `plugins` entry with `isWALArchiver`, and a `ScheduledBackup` whose first base backup is immediate -- WAL alone restores nothing.
- **Every install's archive is its own.** The Cluster archives under a server name of the cluster name plus the first eight characters of the platform's UID (`plugins[].parameters.serverName`, a parameter the plugin supports at v0.13.0), so a reinstall into the same bucket and a restored platform archiving beside its source never collide with an archive Barman would refuse. `status.backup.serverName` prints it.
- **`spec.database.postgresql.recoverFrom`.** Restores a fresh platform's database from a source's archive: the source's `objectStore`, its `serverName`, an optional `targetTime`. Rendered as `bootstrap.recovery` from an `externalClusters` entry addressed through the plugin, with a second `ObjectStore` for the source (no retention). Honored only when the Cluster is first created: a live Cluster keeps its bootstrap (the operator copies it onto the desired object so the re-apply never fights it), and `recoverFrom` declared later is explained in status with the procedure (delete the platform, delete its volume claim, declare it again).
- **`spec.prerequisites.postgresBackupPlugin: auto | skip`.** The Barman Cloud plugin becomes the operator's third shared sub-operator, beside CloudNativePG and Tekton: the same detect-or-install gate (definition `objectstores.barmancloud.cnpg.io`, Deployment `plugin-barman-cloud`, namespace `cnpg-system` -- the only namespace CloudNativePG discovers plugins in) and the same janitor, swept **before** CloudNativePG because the two share a namespace. `auto` installs it whenever the operator installed CloudNativePG itself and cert-manager serves both kinds the chart renders (Issuer and Certificate), or whenever a backup is declared -- so every PostgreSQL an adopter deploys through Planton can back itself up without a toggle, and a cluster without cert-manager pays nothing. The chart is vendored at `0.7.0` (plugin `v0.13.0`, `make pull-chart-barman-plugin`), the same pin the catalog's `KubernetesCnpgBarmanCloudPlugin` renders, and rendered through the same Helm path the platform's charts use, into a sub-operator release rather than a platform-owned object.
- **`status.backup` and a `Backup` print column.** `state` is `NotConfigured`, `Unavailable` (cert-manager absent, or the plugin could not be installed -- the message names the remedy), `Deploying`, `Healthy`, or `Failing` (the plugin's own sentence, relayed from CloudNativePG's `ContinuousArchiving` condition or the failed `Backup` object's error); with `serverName`, `firstRecoverabilityPoint`, `lastSuccessfulBackup`, `lastFailedBackup`. A `BackupHealthy` condition follows it and is deliberately not an input to `Ready`: a failing backup never turns a working platform red, and the PostgreSQL component's own message repeats it beside the health sentence.
- **Two orderings for the person's sake.** A fresh install with a backup declared waits for the plugin before creating its database, so it is born archiving and never restarts for it; a running platform that declares a backup attaches the plugin live, and the status names the one restart before it happens. A Cluster never carries a `plugins` entry before the plugin serves (a Cluster naming an unreachable plugin is parked by CloudNativePG with no instances), and a plugin that cannot be installed never takes the database with it.
- **Readiness explains itself when instances are up.** The PostgreSQL component relays CloudNativePG's phase reason when every instance is ready but the cluster is not, instead of a "waiting for instances" that is not true.
- **RBAC.** `barmancloud.cnpg.io/objectstores` and `postgresql.cnpg.io/scheduledbackups` (full), `backups` (read), `barmancloud.cnpg.io/*` list for the janitor's in-use check, `cert-manager.io` issuers and certificates for the sweep. The chart's `values.yaml` and README name the third sub-operator and the cert-manager prerequisite for backups.

## Why

A self-hosted Planton keeps everything it knows in one PostgreSQL cluster on one volume in the customer's cluster, and until now nothing copied it anywhere; deleting the platform took the database and its credentials as one unit by design, so the only recovery story was a backup, and there was none. Worse, CloudNativePG's backup engine is a plugin the operator did not install, so any PostgreSQL an adopter deployed through Planton with a backup block was parked by the database operator with no instances. Whoever installed CloudNativePG owns its plugin; the operator installed it, so the operator installs the plugin -- at the catalog's pin, so the two paths cannot drift -- and the platform's own backup becomes a declaration whose failures are a column rather than a silence discovered at restore time. The state that is not covered is named rather than implied: the secrets manager keeps its data on its own volume, outside this backup, and is recorded as the next design item (its PostgreSQL storage backend would make one database one backup).

## How to check

```bash
cd operator
make manifests generate && git diff --exit-code config/ ../helm/planton-operator/templates/crds ../helm/planton-operator/rbac
make lint && make test
# The render maps, the plugin loader, the backup arm's decisions, and the condition:
go test ./internal/resources/ -run 'Barman|ObjectStore|ScheduledBackup|PostgreSQLCluster_(NoBackup|Backup|Recovery)|R2S3Endpoint|BackupServerName'
go test ./internal/component/ -run 'DecideBackupPlugin|PlanBackup|KeepLiveBootstrap|RefreshBackupStatus|SharedSubOperators'
go test ./internal/status/ -run 'BackupCondition|ReadyConditionIgnoresBackup'
```

The live proof -- a platform declared without a backup on a cluster without cert-manager reaching Ready with `Backup` reading `NotConfigured`; cert-manager arriving and the plugin installing on its own; a backup declared on the running platform attaching with one named restart and turning `Healthy` against an in-cluster S3-compatible store; a second platform born archiving with zero restarts; wrong keys turning the column `Failing` in the plugin's words with the platform still Ready; a marker written before a base backup and another after it both present in a platform declared again with `recoverFrom`; and the plugin leaving with the last platform unless a stranger's `ObjectStore` keeps it -- is the self-hosted lab's backup lane, to be run in its verification pass.
