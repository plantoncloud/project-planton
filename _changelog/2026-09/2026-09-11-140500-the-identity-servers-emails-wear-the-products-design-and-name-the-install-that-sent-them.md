# The identity server's emails wear the product's design and name the install that sent them

## What changed

- **The identity server's emails are Planton's.** The theme's `email` type, which until now inherited Keycloak's stock templates whole, carries the product's design: a generated FreeMarker layout (`email/html/template.ftl`, `email/text/template.ftl`) with the same wordmark, type, button, and footer as every email the platform's control plane sends, and authored bodies for the password reset, the administrator's account-action request, the verification link, and the admin console's test message, each in HTML and plain text with the subject and inbox preview in the product's voice. Messages this theme does not author (the event notifications) inherit Keycloak's body inside the same frame. A teammate who clicks "Forgot password?" on a self-hosted install now receives an email that looks like the sign-in page they will meet a minute later.
- **The emails name the install, not Planton.** The email type's manifest is rendered per install: the operator writes the platform's sending name (`spec.email.from.name`, the product name when nothing is declared), the front door's URL and host, and `spec.email.replyTo` into `email/theme.properties` as theme properties, and the templates read them (`properties.brandName`, `properties.consoleHost`, `properties.replyTo`). The footer reads "Sent by Acme Platform from planton.acme.com. Questions? Write to it-help@acme.com." and the body says "your Acme Platform account". A renamed sender or a moved console changes the theme hash and rolls the identity pod once, so the next email says the new words.
- **The layout is generated from the platform's email design, never hand-copied.** The platform repository authors every email as React Email and compiles the shared layout and its atoms into these macros (`emailLayout`, `heading`, `paragraph`, `muted`, `button`, `fallbackLink`, `facts`, `fact`, `code`, `textLayout`); its `make email-templates` writes the two files into this theme. An invitation from the control plane and a password reset from the identity server are one design by construction, and a design change is one change in one place.
- **The theme package is a real directory, embedded whole.** `internal/keycloaklogintheme` moves from one Go string constant per artifact to `theme/` laid out exactly as Keycloak reads it (`login/`, `email/`), embedded with `go:embed`. Each file is edited in its own language, the generator writes a file rather than Go source, and the directory listing is the manifest of what ships. `Files(facts)` and `Hash(facts)` take the install's `EmailFacts`; the contents of the login theme are byte-identical to before.
- **The realm-convergence suite renders the emails through a real Keycloak.** The Docker-gated suite now boots Keycloak 26.3 with this theme mounted and `--spi-theme--default=planton` set, beside a Mailpit relay on the same network, and `TestEmailTheme_RendersThroughKeycloak` asks for an account-action email and reads it back from the inbox: the generated layout is FreeMarker the server accepts, the subject is the theme's, the install's facts reach the words, the action link and both renderings arrive, and no template syntax survives. `make test-realm-convergence` runs it with the rest.

## Why

The password-reset email is often the first email a teammate receives from a self-hosted Planton; Keycloak's stock message under a Planton sign-in page broke the one-product feel every other screen holds. Generating the frame from the platform's own email design, rather than restyling it by hand, is what keeps the two senders from drifting apart, and rendering the install's facts into the theme is the only channel a Keycloak email template has to learn whose install it runs on. No incumbent shares one email design between its product and its identity server; the operator now does, on the same ConfigMap delivery that keeps the official Keycloak image unmodified.

## How to check

```bash
cd operator && go test ./internal/keycloaklogintheme ./internal/resources ./internal/component   # the artifacts, the rendered facts, the generated layout's shape, the ConfigMap and hash
cd operator && make test-realm-convergence     # a real Keycloak with the theme: an account-action email rendered through the generated layout, read back from Mailpit with the install's name, console, reply-to, link, and both parts
```

Live: on a Kind cluster with this operator and `spec.email` declared, "Forgot password?" on the sign-in page lands an email whose header reads the install's sending name, whose button says "Choose a New Password", and whose footer names the install's console host and reply-to; the identity pod rolls once on this operator release for the changed theme.
