# MongoDB and Postgres on GKE back up to GCS and restore from it, proven live

## What changed

- **KubernetesMongodb has a restore arm and honest GCS credentials.** `spec.restore` declares a `PerconaServerMongoDBRestore` (from a Backup object by name, or from a location in one of the cluster's storages, with point-in-time recovery to `latest` or a date, and replica-set remapping); `spec.system_users_secret_name` brings the source cluster's system-users Secret so the restored data's users and passwords work. The GCS storage's `service_account_key_json` string is gone; `gcs.credentials` is required and carries either `service_account_key` (a reference, typically to a `GcpServiceAccount`'s `key_base64` output) or `existing_secret_name`. The earlier "empty means Workload Identity" claim was false: the operator's CRD requires the credentials Secret and Percona Backup for MongoDB has no keyless GCS path. The restore object carries the storage definition inside `backupSource` because the operator resolves a backup-source restore's storage from the restore itself when it syncs the store's metadata into a fresh cluster.
- **KubernetesPostgres recovery keeps the source's credentials.** `bootstrap.recovery` gains `database`, `owner`, and `owner_secret_name`, so a cluster bootstrapped from an archive hands out the source's application password rather than a fresh one. The GCS keyless field documents the two bucket roles the identity needs (`roles/storage.objectAdmin` and `roles/storage.legacyBucketReader`): Barman Cloud probes the bucket before every WAL archive, and `objectAdmin` alone fails every archive.
- **KubernetesCloudNativePgOperator can add only the Barman Cloud plugin.** `install_operator: false` skips the operator release and its CRDs and installs the plugin beside a CloudNativePG that is already on the cluster (a self-hosted Planton installs one without the plugin). Validation refuses the posture without the plugin enabled, or with operator-only settings that would silently do nothing. Destroying a plugin-only declaration leaves the resident operator running.
- **The E2E runner learned real clusters.** A scenario can substitute a kind's install profile (`planton.dev/e2e-prerequisite-install-manifest: "Kind=path"`), declare a kind already resident on the lane's cluster (`planton.dev/e2e-resident-prerequisites`, only on real-cluster profiles), and read values a setup script published (`${E2E_SETUP:NAME}`) into the manifest before validation. The `gcp-gke` profile joins `aws-eks`; its batch under `catalog/kubernetes/aa_e2e/realcluster/gcp-gke/` creates the GCP side (identities, Workload Identity bindings, the bucket) from the catalog's own kinds through `planton apply -f`.
- **New presets and guide sections.** `kubernetesmongodb/03-gke-replica-set-gcs-backups`, `kubernetespostgres/04-gke-ha-gcs-backups`, and a "Disaster recovery on GKE: the resource set" section in each kind's GUIDE listing every catalog resource the posture needs and the two rules it stands on (credential continuity; one archive path per cluster).

## Why

An early adopter asked whether Planton can run a highly available MongoDB on GKE that backs itself up and can be restored, and the same for Postgres. Both kinds were proven on a laptop cluster with backups to an in-cluster MinIO; restore had never been executed, and nothing had run on GKE. Proving it live found the gaps above: the false keyless claim would have been rejected by the API server at the adopter's first apply, neither kind modeled the credential-continuity requirement both operators document, and the operator kind could not add the backup plugin beside the CloudNativePG the platform itself installs.

## How to check

```bash
go test ./catalog/kubernetes/kubernetesmongodb/... ./catalog/kubernetes/kubernetespostgres/... ./catalog/kubernetes/kubernetescloudnativepgoperator/... ./e2e/framework/...
```

Live, on a GKE cluster (both engines were green on 2026-09-09): `source` the batch's `env.sh` after `realcluster/gcp-gke/bootstrap.sh`, then run `TestKubernetesPostgres_<Engine>/gke-gcs-recovery` and `TestKubernetesMongodb_<Engine>/gke-gcs-restore` with `-tags=e2e`. Each lane deploys a three-instance source spread over three nodes, seeds a marker, takes a backup into the real bucket, seeds a second marker after it, then bootstraps a fresh cluster from the archive and reads both markers back through the source's own credential Secret. `TestKubernetesCloudNativePgOperator_<Engine>/plugin-only` on the kind cluster proves the plugin-only posture and that destroying it leaves the resident operator alone.
