# The identity server sends through the declared mail provider, and "Forgot password?" works

## What changed

- **The realm's mail settings are owned from `spec.email`.** The realm reconciler now owns two more realm-level settings: `smtpServer`, converged by key from the platform's one email declaration (host, port, the security word mapped literally onto Keycloak's `starttls`/`ssl` booleans, the sender identity, the sign-in mode -- a password, an OAuth2 client-credentials token as `authType=token` with the four token facts, or none -- and the user), and `resetPasswordAllowed`, `true` exactly when a relay is declared. So the sign-in page offers "Forgot password?" when an email can actually be sent, and the reset email arrives from the install's own address through the same relay invitations go through. A platform on the Resend arm gives the realm Resend's SMTP endpoint (`smtp.resend.com:465`, implicit TLS, user `resend`, the API key as the password), so one declaration powers both senders. When nothing is declared the operator owns the off-state too: no relay, reset off -- a relay typed into the identity server's admin console cannot make the sign-in page contradict what the product advertises.
- **The relay password never lingers and never leaks.** Keycloak masks the SMTP password and the OAuth2 client secret on read, so the operator fingerprints the credential it hands over in its realm-state Secret and writes the masked keys on rotation; a rotated Kubernetes Secret reaches the realm on the next reconcile with no restart, reported by key (`smtpServer.password (rotated)`), never as a value. Every write that touches `smtpServer` carries the real secret with it, because Keycloak drops a masked secret that arrives with a moved destination. A credential key the declaration no longer renders (a password after a switch to token sign-in) is removed, not left behind. A referenced Secret that cannot be read leaves the realm's mail settings exactly as they are for that pass; the control plane already reports that finding, and the identity server keeps serving sign-ins.
- **The relay's private CA joins Keycloak's truststore.** `spec.email.smtp.caBundleSecretRef` is mounted at `/opt/keycloak/conf/email-ca/email-ca.crt` beside the directory arm's CA and listed in `KC_TRUSTSTORE_PATHS`, which Keycloak's SMTP sender verifies the relay's certificate against; a changed bundle rolls the identity pod once (truststores are read at start), the one restart email ever costs the identity server.
- **One realm-state record, one writer.** The operator's bookkeeping Secret is now `{name}-identity-realm-state` with `federation-credential-sha256`, `oidc-endpoints`, and `email-credential-sha256`, read once and written once per pass (server-side apply under one field manager would otherwise drop a second writer's keys). A replayed pass keeps the recorded broker endpoints instead of dropping them.
- **The Planton theme gains an `email` type.** The server-wide default-theme flag names the theme for every theme type; with no `email` type Keycloak could not render a single message ("Failed to find EMAIL theme planton"). The type inherits Keycloak's bundled email templates whole, so emails render in the server's stock look until branded templates land in that one place. The theme ConfigMap is keyed by flattened path (`login__theme.properties`, `email__theme.properties`) so two types can each carry their manifest.
- **The realm import bakes the email off-state** (`resetPasswordAllowed: false`, `smtpServer: {}`), never a declaration: the import is create-only and rides a Secret whose content hash rolls the pod, so a password in it would roll the identity server on every rotation for nothing. The reconciler owns the declaration seconds after first boot. Existing installs roll the identity pod once on this release for the changed import.
- The basic-auth key names (`username`, `password`) are one exported pair of constants used by the credentials projection, the Secret preflight, and the identity reader.

## Why

One declaration, both senders: an administrator who declared a relay for invitations should not have to declare it a second time, in a second place, for password resets -- and a teammate who forgets a password should get an email from the install, not an admin-console rescue. The identity server has no environment seam for this, so the operator hands the relay to the realm the way it already hands the directory bind credential: owned by key, the secret fingerprinted, rotation written once and steady state never. A note for relay choice: Keycloak's STARTTLS is an opportunistic upgrade where the control plane's arm requires it; a relay that offers implicit TLS (`security: tls`) is the stricter declaration for the identity server's side.

## How to check

```bash
cd operator && go test ./internal/keycloak ./internal/resources ./internal/component ./internal/keycloaklogintheme   # the owned block, the converge rule, the CA mount, the record, the theme type
cd operator && make test-realm-convergence     # a real Keycloak: the block lands and reads back masked, zero writes when converged, one write on rotation, the secret survives a moved host, the off-state clears a typed relay, hands-off leaves one alone
```

Live: on a Kind cluster with this operator, a platform with `spec.email.smtp` at a relay behind a private CA reaches `Ready`; the realm's `smtpServer` carries the relay by key with `password: **********` and `resetPasswordAllowed: true`; `KC_TRUSTSTORE_PATHS` names the relay CA; "Forgot password?" on the sign-in page lands a reset email from the install's own address whose link sets a new password that signs in; rotating the Secret's password reaches the realm within one reconcile with no identity restart and is logged by key; removing `spec.email` turns reset off and clears the relay, and declaring it again brings both back.
